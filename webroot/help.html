What is this module

ipset-arm64 is a dynamic, arm64 Android kernel module that lets you block specific IP addresses or entire network ranges at the firewall level, and control it all from a WebUI - no Termux, no adb, no manual shell commands required for everyday use.

It bundles the ipset binary with a control script (ipctl.sh) and a web interface. Nothing is blocked by default - every set and every firewall rule only exists because you created it.

How IP/network blocking actually works

Two pieces work together:

  • ipset - a fast, indexed list ("set") of IP addresses or CIDR ranges, stored in the kernel. Looking up whether an address is a member of a set is O(1)-ish, unlike checking hundreds of individual iptables rules one by one.
  • iptables - the actual firewall. A single rule says "for any packet whose destination matches this set, DROP it." One rule can reference thousands of addresses at once via the set.

Typical uses: blocking a known malicious server by IP, blocking an entire hosting provider's range (CIDR) that keeps serving abuse traffic, cutting off an app's hardcoded IP that ignores your DNS settings entirely, or building a personal blocklist of ad/telemetry endpoints that resolve to fixed IPs.

ⓘ
Single address vs. range: a single IP (1.2.3.4) blocks just that one host. A CIDR range (1.2.3.0/24) blocks every address in that block at once - useful when a provider rotates through many IPs for the same service.
01

Status

Shows whether your kernel actually supports what this module needs: the ipset binary running correctly, iptables present, and the relevant kernel configs (CONFIG_IP_SET, CONFIG_IP_SET_HASH_IP, CONFIG_IP_SET_HASH_NET, CONFIG_NETFILTER_XT_SET) enabled. Green OK / = y means supported; red means missing.

Also lists every set currently loaded in the kernel and every dynamic rule currently active - a full snapshot of what's actually blocking traffic right now.

02

Sets

A "set" is just a named container for addresses. Create one, pick a type, then add addresses to it. Nothing is blocked yet at this point - creating a set only prepares the list.

Run sh ipctl.sh types for the full list including the bitmap and list types. Which of them actually work is a property of the kernel, not this module - sh ipctl.sh status reports what the running kernel provides.

Sets are IPv4 by default. For an IPv6 set, pick IPv6 in the family dropdown next to the type when creating it, or from the shell: sh ipctl.sh create v6block hash:net inet6.

bitmap:* and hash:mac have no address family — the dropdown disables itself for those.

Once a set exists, tapping it opens Set Detail right below (add/remove addresses). Firewall rules for it are managed separately in section 03 - Config, so you never have to scroll past a huge set's members just to reach the rule controls.

✓
Equivalent raw command: sh ipctl.sh create myset hash:ip then sh ipctl.sh add myset 1.2.3.4.

Set Detail

Appears right below Sets once you tap a set tile (tap again to close it). Only handles members - adding/removing individual IPs or CIDR ranges. This just edits the list; it doesn't block anything by itself. Firewall rules live in Config (section 03) instead, reachable independently via its own set selector - you don't need to open this view at all just to turn a rule on or off.

03

Config

Firewall rule control for any set, always visible - independent of how many members that set has. Pick a set from the dropdown here (separate from tapping a tile in Sets); nothing else needs to be open.

The config box

Four dropdowns define what a rule would look like: chain (OUTPUT/INPUT/FORWARD), direction (dst/src), target (DROP/ACCEPT/REJECT/RETURN), and which set to apply it to.

Per-app filtering (optional)

Below the set selector is a search box - type or paste part of a package name (e.g. instagram) to find an installed app, filtered live from a locally cached list (loaded once, on first tap). Selecting one restricts the rule to that single app's traffic, shown as a chip with a Clear button.

⚠
Only works with chain = OUTPUT. Android's owner match can identify which app originated an outgoing packet, but has no way to attribute incoming traffic (INPUT) to a specific app before it's even been routed anywhere on the device.

Each rule targets exactly one app at a time - to filter several apps, create a separate set per app (or per group) rather than trying to combine them into one rule.

The 3 rule slots

Below the config box are three independent slots, each with its own status badge and button. This is what lets you enforce up to 3 simultaneous rules on the same set - e.g. block both incoming and outgoing traffic at once, or apply different targets per direction.

  • An empty slot just says "Enable rule". Tapping it reads whatever is currently selected in the config box above and creates that exact rule, claimed by that specific slot.
  • An active slot shows "Disable rule <CHAIN>" - naming the chain it's actually enforcing (and the app's uid, if per-app filtering is active). Tapping it removes precisely that rule, regardless of what the config box currently shows.
  • Each slot keeps its own identity across refreshes - enabling slot 2 keeps it in slot 2, it never gets shuffled to slot 1.
  • Trying to enable a combination that's already active in another slot is blocked with an on-screen warning instead of silently creating a duplicate.
  • A set with no addresses yet can't have a rule enabled for it - the button will explain why instead of silently creating a rule that blocks nothing.

Delete entire set automatically disables every active slot for it first, then destroys the set - safe to hit even mid-test, no manual cleanup needed beforehand.

Equivalent raw commands
sh ipctl.sh rule-add myset OUTPUT dst DROP           # first slot
sh ipctl.sh rule-add myset INPUT dst DROP            # second slot, same set
sh ipctl.sh rule-add myset OUTPUT dst DROP 10234     # third slot, restricted to app uid 10234
sh ipctl.sh rule-del myset OUTPUT dst DROP           # disable just that one
sh ipctl.sh apps                                     # list installed packages with their uid
sh ipctl.sh destroy myset                            # only works once no rule is active
04

Active Rules

A flat list of every firewall rule currently enforced by this module, across every set - your at-a-glance "what's actually being blocked right now" view, independent of which set you have open.

05

Connectivity Test

A built-in ping runner. Type any address and check whether it's reachable - handy right after enabling a rule, to confirm the block actually took effect, all without leaving the WebUI or opening Termux.

06

Threat Feeds

Downloads and maintains a managed set called feed_firehol_level1, built from FireHOL's level1 aggregated list - it combines several sources (dshield, feodo/abuse.ch botnet trackers, and Spamhaus DROP) into one feed, so a single update covers more malicious infrastructure than any one source alone. It behaves exactly like any other set (shows up in Sets with an orange FEED tag, gets its rules from Config like normal), except its membership is kept current for you.

✓
FireHOL's raw list also includes IANA "bogon" ranges (private/reserved address space like 192.168.0.0/16, 127.0.0.0/8, and carrier-grade NAT 100.64.0.0/10) meant for filtering traffic arriving at a network edge - not for blocking outbound traffic from a phone. These are excluded before the set is built, so this feed can never block your own WiFi gateway, mobile carrier NAT, or loopback traffic.
  • Update Now - fetches the current list, excludes the fixed bogon ranges, deduplicates, and atomically swaps it in. No traffic gap: the old set stays enforced right up until the new one is fully built. Every update fully replaces the set's contents - nothing from the previous version lingers alongside the new entries.
⚠
Requires curl or wget on the device. Most root managers ship with busybox, which provides wget - if neither is found, Update Now will say so explicitly instead of failing silently.
07

Boot Restore Log

Every reboot, service.sh automatically reloads whatever sets and rules you had active before shutting down. This panel shows exactly what happened during that process on the last boot - useful for confirming persistence is working, or diagnosing why a rule didn't come back.

08

Command Log

A rolling history (last 30 entries) of every command this WebUI has run in the current session, with the raw output. Newest at the bottom - scroll up to review earlier actions. The size badge next to Clear shows how much this session's log currently holds in memory (not a file on disk).

09

Persistence, updates & reflashing

Your sets, rules, and threat feed state are saved to /data/adb/ipset_arm64_data/ - deliberately outside the module's own folder.

ⓘ
When a Magisk/KernelSU module is updated, the manager replaces its entire folder with the new zip's contents. Anything stored inside the module's own directory would be wiped on every update. Storing data externally means you can reflash a new version of this module - to pick up new features or fixes - and your existing sets, rules, feed subscription, and boot log all survive untouched.

On every boot, service.sh reads this external data and reapplies it automatically - no action needed from you.

10

Uninstalling

Removing the module through your manager's normal uninstall flow runs uninstall.sh automatically, which:

  • Removes every active firewall rule this module created (kernel-level, not just files)
  • Destroys every ipset set loaded in the kernel, including the threat feed set
  • Deletes the external data directory (/data/adb/ipset_arm64_data/)

The device is left exactly as if the module was never installed - no orphaned rules silently blocking traffic after removal.

Using this alongside dnscrypt-proxy-android-arm64-only

dnscrypt-proxy-android-arm64-only is a companion module - they solve different problems and are safe to run together.

dnscrypt-proxyipset-arm64
Operates atDNS layerIP/packet layer
Blocks bydomain nameIP address / CIDR range
Stopsthe lookup, before an IP is even resolvedthe connection, after an IP is known
Blind spotapps with hardcoded IPs or their own DoH that skip your resolverdoesn't know domain names, only addresses

Running both gives you layered coverage: dnscrypt-proxy blocks known-bad domains before your device ever asks "what's the IP for this?" - cheap and broad. ipset-arm64 catches what DNS-level filtering can't: apps that bypass your DNS settings entirely and connect straight to a hardcoded IP, or CDN/hosting ranges you want blocked regardless of which domain resolves there.

✓
No conflict between them - dnscrypt-proxy touches DNS traffic (port 53/853), ipset-arm64 touches whatever chain/rule you configure. They don't compete for the same packets unless you explicitly set one up to.

Full command reference

For advanced use directly via adb shell / Termux (su) - everything the WebUI does maps to one of these.

ipctl.sh
sh /data/adb/modules/ipset_arm64/ipctl.sh status
sh /data/adb/modules/ipset_arm64/ipctl.sh list [setname]
sh /data/adb/modules/ipset_arm64/ipctl.sh create <name> [type] [inet|inet6]
sh /data/adb/modules/ipset_arm64/ipctl.sh destroy <name>
sh /data/adb/modules/ipset_arm64/ipctl.sh add <name> <ip>
sh /data/adb/modules/ipset_arm64/ipctl.sh del <name> <ip>
sh /data/adb/modules/ipset_arm64/ipctl.sh test <name> <ip>
sh /data/adb/modules/ipset_arm64/ipctl.sh rule-add <name> [chain] [dir] [target]
sh /data/adb/modules/ipset_arm64/ipctl.sh rule-del <name> [chain] [dir] [target]
sh /data/adb/modules/ipset_arm64/ipctl.sh rules
sh /data/adb/modules/ipset_arm64/ipctl.sh bootlog
sh /data/adb/modules/ipset_arm64/ipctl.sh feed-update
sh /data/adb/modules/ipset_arm64/ipctl.sh feed-status
sh /data/adb/modules/ipset_arm64/ipctl.sh save
sh /data/adb/modules/ipset_arm64/ipctl.sh restore
sh /data/adb/modules/ipset_arm64/ipctl.sh flush-all

rule-add/rule-del defaults: chain=OUTPUT, dir=dst, target=DROP. A set can carry up to 3 simultaneous rules this way - just call rule-add again with a different chain or direction. flush-all removes every set and rule this module created - tracked in an ownership manifest, so sets belonging to other apps (a firewall, a VPN, your own scripts) are never touched. Used internally by uninstall.sh, and safe to run manually for a clean slate.

For the same reason, destroy refuses to remove a set this module did not create. Use the ipset binary directly if that is really what you want.
